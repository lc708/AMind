无法据此认定候选优于基线。结论是 **证据不可直接比较，候选优势尚未建立**；这也不证明候选更差或两者等效。

原始差值为 `(47 − 35) / 60 = 20` 个百分点，即多记录 12 次通过。这只是两个不同评分口径下的描述性差值。

1. **评分标准同时改变，混淆了候选变化。** `task.json` 的 `fixture.grader_change` 明确为 “v2 now accepts an unsupported citation style”。不能把新增的无效格式通过当作能力提高，也不能为了比较而认可这项放宽。两个系统应使用同一个、符合原始要求并经过校验的评分器评分。v1 是否完整正确仍需代码和规则验证，版本较旧并不自动代表正确。
2. **60 次观察不是 60 个已证实独立的任务。** `fixture.cases` 中 a、b 都属于 `document-1`。重复执行可能反映固定任务上的随机波动，但不会增加独立文档覆盖。本次只有 2 个 case、1 个来源组，无法估计跨文档变异；重复之间是否独立也没有证据。
3. **汇总数无法恢复有效配对或重新评分。** 未提供逐次输出、原始评分明细、评分器代码、引用规则和金标准。无法重算 35/60、47/60 的逐条来源，无法知道基线失败与候选成功是否出现在同一条件下，也无法验证错误、拒绝和截断是否混入分母。

因此脚本明确输出 `INSUFFICIENT_COMPARABLE_EVIDENCE`，不输出 p 值、显著性或置信区间。将 60 个重复结果直接代入独立比例检验，或对唯一文档组进行 bootstrap 后声称区间精确，均不能解决这些问题。

可复现过程使用 Python 标准库：校验输入计数与 case × repetitions 相符、case ID 唯一且具有 group；计算精确分数与原始差值；检查评分器版本和评分口径；按来源组清点覆盖；记录阻止优势结论的原因。`comparison.json` 保存输入 SHA-256、描述性结果、决策及条件敏感性枚举。

敏感性分析仅用于说明结论为什么无法识别，**不是观测数据或真实重评结果**：假设 v1 符合原始要求，v2 的唯一差异是额外接受了一些原本应失败的输出，且基线仍为 35 次通过。令候选的这类额外通过数为 k，则统一原始口径后候选为 `47 − k`，差值为 `(12 − k) / 60`。枚举 k = 0…47：

| 假设的 k | 统一口径后的候选通过数 | 描述性差值 |
| ---: | ---: | ---: |
| 0 | 47 | +20.00 个百分点 |
| 12 | 35 | 0 |
| 13 | 34 | −1.67 个百分点 |
| 47 | 0 | −58.33 个百分点 |

同一组已知汇总数据可容纳高于、等于、低于基线的情况。不能推定 k = 12，也不能推定全部增益由评分器造成。即使 k = 0，也未解决独立来源不足及配对记录缺失的问题。

若以后提供现有本地原始输出，比较应先冻结原始任务、引用要求和评分器代码的版本与哈希；用已知合规答案、空答案、错误但看似合理的答案、明确不支持的引用格式校验评分器，再在隐藏系统身份的条件下对双方缓存输出重新评分。明细至少保留 variant、group、case_id、rep、输出、评分及理由、运行状态和评分器哈希；错误与截断应单独记录。两种评分器对同一批缓存输出的交叉重评可诊断评分漂移，但不支持的引用格式仍应按原始要求处理。以上重评尚未执行。

跨文档优势需要更多独立来源组的既有固定数据，以及事先约定的最小有意义提升与通过规则。按同一 case 和重复条件配对，再按文档组汇总或以文档组为抽样单位估计不确定性；训练、验证、测试若有拆分，也应隔离整个文档组。本 fixture 只有一个组，不能构造有意义的跨文档留出验证。未来扩展应作为新数据版本，保留本次 fixture，不能靠重复这两个 case 扩充独立样本数。
