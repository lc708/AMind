# AMind 应用技能与 claude-api 的全面对照

> 这是升级前的历史基线报告，针对 Engineering 0.1.0 / Eval Improve 0.2.0。后续能力内核改造和当前证据见[新版验收记录](2026-09-30-capability-core-verification.zh-CN.md)。以下结论保留当时的判断。

审查日期：2026-09-30。审查对象：本仓库 `amind-engineering 0.1.0`、`eval-improve 0.2.0`，以及 Anthropic 官方 `claude-api` 在提交 `8a1541c4a3ffa5a20a5a91de0dcf3f0bab1d1ef4` 中的公开内容。

通过 GitHub 提交 API 核对，截至本次查询，`skills/claude-api` 最新修改仍是该提交，时间为 2026-09-29T02:20:03Z。下载了该目录全部 81 个文件，并校验其 Git blob 哈希。AMind 两个技能共 24 个文件；本次读取全部工作流及 Python 工具，审查上游工作流、评测骨架、状态协议和语言参考目录，并执行离线探针。没有进行模型质量对比，也没有调用真实目标模型或付费 API。

## 结论

**当前 AMind 是面向 Codex 的精简适配版，并在少数评测设计点上有所改进；还不是 claude-api 的完整等价迁移，更没有证据证明整体更好。**

- `amind-engineering` 的优势是适合当前用户的 Codex/OpenAI 环境、入口清楚、保留已有授权和模型选择。主要弱点是把许多具体工程知识压缩成了待执行的检查清单，工作流名称对应不代表实现深度相等。
- `eval-improve` 保留了正确的评测原则，增加了可执行的配对比较和明确的验证集/最终测试集区分。主要弱点是缺少原版更完整的通用运行骨架，且现有采集器存在可复现的轨迹覆盖问题。
- 对当前“不使用 Claude”的需求，迁移方向合理。合理的下一步是补齐工程工具和 OpenAI 对应实例，而不是恢复 Claude 依赖或增加更多模式名称。

此前“覆盖八个主要工作流”的交付表述只能理解为**八种任务意图均有路由和说明**，不能解释成等量知识、工具或能力已经迁移。

## 比较依据与边界

本报告区分三类证据：

1. **源码确认**：文件中有明确指令、代码、接口或缺失项。
2. **离线复现**：用合成数据和模拟进程实际验证了某项软件行为。
3. **专业判断**：由上述事实推断使用上的利弊；不是实际模型效果分数。

原版面向 Claude 技术栈，AMind 面向 Codex/OpenAI。比较具体能力时，看各自在目标技术栈中的工程支持深度，不要求复制不适用的 Claude 字段、服务或认证方式。两者都是供代理使用的技能和工具集合，都不是对任意产品开箱即用的自动优化服务。

## 已确认的优势，及不应扩大解释的地方

### 1. Codex 适配是有效工作，但不是能力超越

AMind 去除了必须使用 Claude 产品的执行前提，区分了“运行技能的代理”“被评测应用”“评分模型”，也区分订阅额度和 API 账单。这符合用户需求。原版针对自己平台提供专门知识，本身不是缺陷；真正要比较的是 AMind 是否为目标平台补出了同等深度的配方和工具，目前没有。

证据：[AMind 工程入口](../skills/amind-engineering/SKILL.md)、[评测入口](../skills/eval-improve/SKILL.md)、[上游入口](https://github.com/anthropics/skills/blob/8a1541c4a3ffa5a20a5a91de0dcf3f0bab1d1ef4/skills/claude-api/SKILL.md)。

### 2. 最终测试与选择过程的关系更清楚

AMind 明确把反复用于选择候选的分数称作 validation，把 final test 留到候选冻结后。原版通用 hillclimb 第 207 行仍默认每轮用 test 分数选择获胜轮次，第 209 行才给出三分法选项。

但不能说原版完全没有认识这个问题：它的成本爬坡指南第 357 行明确指出，参与选优的集合属于选择集，不因名字叫 test 而成为最终留出集。AMind 的优势是把这一口径贯彻为通用默认规则。

证据：[AMind 的拆分规则](../skills/eval-improve/references/hillclimb.md)、[原版通用规则](https://github.com/anthropics/skills/blob/8a1541c4a3ffa5a20a5a91de0dcf3f0bab1d1ef4/skills/claude-api/shared/evals/eval-hillclimb.md#L205)、[原版成本测量规则](https://github.com/anthropics/skills/blob/8a1541c4a3ffa5a20a5a91de0dcf3f0bab1d1ef4/skills/claude-api/shared/evals/cost-hillclimb.md#L348)。

### 3. 配对比较器是实质新增，但有清楚边界

AMind 先在每个 case 内平均重复结果，再比较相同 case 的差异；缺失、重复、额外重复次数、非有限分数或未评分状态会阻止完整比较。按独立 case 重采样，比直接把重复尝试全部当成新增独立样本更符合面向任务分布的推断。

这不能升级为“统计上全面优于原版”：脚本不处理相关 case 的自动分组、不校正反复选优、不自动实现质量非劣检验，也不校验数据/评分器身份。极小样本或相同观察差异可产生退化区间，不能作为泛化保证。原版通用文档将区间重叠作为零差异依据也不严谨；应直接估计配对差异的不确定性。

证据：[比较代码](../skills/eval-improve/scripts/compare_runs.py)、[使用限制](../skills/eval-improve/references/artifacts.md)、[原版最终决策表述](https://github.com/anthropics/skills/blob/8a1541c4a3ffa5a20a5a91de0dcf3f0bab1d1ef4/skills/claude-api/shared/evals/eval-hillclimb.md#L304)。

## 主要差距

### 1. 工程技能失去了很多具体知识

例如，AMind 的模型/API 迁移与 SDK 升级共用一个 22 行参考文件，主要要求代理盘点、查文档、改代码、做验证。原版包含具体模型迁移章节和专门 SDK 升级说明。差距不在字数本身，而在原版给出许多“遇到该触发条件时如何改、为何要改、怎样核对”的具体答案，AMind 把这些答案重新交给运行时研究。

这在方向不明确的早期讨论中尚可，在复杂存量项目、多语言集成、版本升级和排错中会增加漏项和重复研究的可能性。要补的是 OpenAI 对应的经验证实例，不是机械增加文档长度。

证据：[AMind 迁移说明](../skills/amind-engineering/references/migration.md)、[上游迁移参考](https://github.com/anthropics/skills/blob/8a1541c4a3ffa5a20a5a91de0dcf3f0bab1d1ef4/skills/claude-api/shared/model-migration.md)、[上游 Python 升级参考](https://github.com/anthropics/skills/blob/8a1541c4a3ffa5a20a5a91de0dcf3f0bab1d1ef4/skills/claude-api/python/claude-api/sdk-upgrade.md)。

### 2. 独立成本优化实验流程没有完整迁移

原版不只罗列缓存、短提示词、小模型等选项，还有单独的实验搜索策略：分阶段探索模型与推理强度、冻结部分变量、预先约定采用条件、要求预期机制出现在实际测量中、对合并配置再作确认。AMind 目前只有原则清单和通用迭代说明。

迁移应该保留这些可跨平台使用的方法，替换提供商参数与计费实现。本次没有完整做到。

证据：[AMind 成本说明](../skills/amind-engineering/references/cost-optimization.md)、[上游成本实验流程](https://github.com/anthropics/skills/blob/8a1541c4a3ffa5a20a5a91de0dcf3f0bab1d1ef4/skills/claude-api/shared/evals/cost-hillclimb.md)。

### 3. 采集器不能替代通用评测引擎

AMind 的 `collect_codex.py` 有计划模式、次数限制、超时、原始事件保存，成功输出明确保持 ungraded。这些设计有用，但它只接收文本任务，固定只读新会话，不执行项目评分器，不支持同一 variant 续跑、内置并发或重试。

原版骨架也不是即用产品：必须补 `loadCases`、`runCase`、`gradeCase` 三个函数。但这些接入点背后已经有更多通用执行逻辑。AMind 要评测任意产品仍需临场生成这部分代码，不能声称工具能力已经等价。

证据：[AMind 采集器](../skills/eval-improve/scripts/collect_codex.py)、[采集限制](../skills/eval-improve/references/codex-runner.md)、[原版运行骨架](https://github.com/anthropics/skills/blob/8a1541c4a3ffa5a20a5a91de0dcf3f0bab1d1ef4/skills/claude-api/shared/evals/report/runner-scaffold.mjs)。

### 4. 文字要求尚未成为执行保障

AMind 要求固定数据、评分器和配置，但比较器实际读取的是全局状态中的 ID 与结果分数，忽略各 variant 的运行清单。采集器虽然记录部分哈希，却不将它们传递成比较前的强制检查。目标版本还是调用者填写的标签；工作区内容、技能版本、有效配置和模型身份没有自动完整封存。

双方都不能仅靠指令或只读设置保证优化器看不到答案。原版提出独立分析角色和结构隔离；AMind 说明了这个问题，却没有提供隔离执行实现。不能把“文档提醒过”记为“已实现隔离”。

## 离线复现

全部使用合成数据和模拟运行函数，没有调用模型。原始观察保存于本地 `.codex-tmp/amind-claude-api-audit-2026-09-30/offline-probes.json`，下面保留不依赖临时目录路径的关键结果。

| 探针 | 实际结果 | 含义 |
|---|---|---|
| AMind 原有应用测试 | 23/23 通过 | 既有检查通过，不代表未覆盖行为正确 |
| AMind 输入 ID 为 `A` 和 `a`，本机不区分大小写的文件系统 | 返回码 0，报告完成 2 个任务；captures 有两行，但 traces 只剩一份且内容为第二个任务 | **确认的轨迹覆盖缺陷** |
| 原版骨架接入两个模拟任务与评分器 | 两条 `status: ok` 的评分记录 | 模板在补齐接入点后能够端到端生成评分记录 |
| 原版同一 variant 再执行 | 不增加模拟应用调用次数，仍为 2 次 | 续跑逻辑工作 |
| 原版登记后修改运行器 | 返回码 2，不增加应用调用 | 运行器变更检查工作；不等于完整防篡改边界 |
| 原版输入 ID 为 `A` 和 `a` | 执行任务前拒绝，返回码 2 | 原版已处理同类文件名冲突 |
| AMind 基线和候选清单的 cases/state 哈希不同，但 ID、重复数和成绩齐全 | 比较器仍返回 `improvement_clears_threshold` | **确认的身份校验缺口**；现有文档已披露此限制，但执行链未强制保证 |

轨迹覆盖缺陷对应采集器 `prepare()` 的区分大小写 ID 检查与 `capture()` 的直接文件名拼接。它不一定丢失 captures 内的最终文本，但会覆盖单独轨迹和同名原始事件，破坏逐案例溯源。修正方式可以是执行前检查大小写归一后的冲突，或使用稳定、无冲突的文件名映射；应补回归测试。

此前宣布的 46 项测试，构成为 23 项新应用脚本/安装检查和 23 项原 AMind 知识包回归。它们没有验证八种工程工作流在真实项目上的行为，也没有证明迁移完整性。本次只重跑应用侧 23 项，另执行上述针对性探针。

## 应保留、应补齐、应验证

**应保留：** Codex 适配、两个模块的职责划分、已有授权沿用、提供商与运行环境的区分、严格完整配对检查、验证集/最终测试的明确规则、Apache 归属说明。

**优先补齐：**

1. 修正大小写冲突；让比较之前必须校验可比较的数据、评分器和配置身份，并正确区分输入内容哈希与允许变动的目标实现。
2. 建立 provider-neutral 的应用执行/评分接口，支持真实 API、函数和命令；补续跑、并发、重试、失败成本、环境快照。Codex 采集器成为其中一种适配器。
3. 补 OpenAI Python/TypeScript 的可运行配方：工具循环、流式、结构化输出、会话/压缩、错误处理、迁移与升级。链接官方文档作为更新依据，而不是唯一实现知识。
4. 完整迁移跨平台成本搜索方法，并明确数据保留、实际环境副作用、评分校准和最终验收的操作步骤。
5. 为需写文件的 coding agent、多轮会话和有副作用的工具任务补真实入口与隔离夹具；不扩大现有只读采集器的能力声明。
